# FleetAMP v0.2.0 end-to-end demo and presentation runbook

This runbook validates the v0.2.0 governed fleet-management loop and produces
a consistent set of screenshots for a presentation or short demo video.

## Test objective

Demonstrate that FleetAMP can identify a Collector, place it under group
ownership, validate a configuration change, separate request from approval,
deploy safely, show runtime state and preserve an audit trail.

## Environment

Use an isolated test environment, not a production Collector.

- FleetAMP v0.2.0 release candidate
- One OpAMP Supervisor-managed `otelcol-contrib` Collector
- One Admin account
- One Group Owner account
- Optional SMTP test inbox
- Optional exact Collector binary configured through
  `FLEETAMP_OTELCOL_BINARY`

The Compose lab uses <http://127.0.0.1:18080>. Keep its volumes between demo
runs when stable Collector identity and history are part of the presentation.

## Automated navigation and validation smoke test

After FleetAMP is running and the first Admin exists:

```bash
export FLEETAMP_BASE_URL=http://127.0.0.1:18080
export FLEETAMP_ADMIN_USERNAME=admin
export FLEETAMP_ADMIN_PASSWORD='replace-with-demo-password'
./scripts/e2e-demo-smoke.sh
```

The script checks health, login/session handling, every main navigation page,
all three Administration pages, valid YAML acceptance and invalid YAML
rejection. It prints TAP-style results and does not create or delete resources.

Do not record a terminal containing the password environment variable. Clear
the variable or close the terminal after the test.

## End-to-end governed-change scenario

### 1. Establish the Collector

1. Start FleetAMP and the Supervisor-managed Collector.
2. Open **Fleet** and confirm the Collector is Healthy.
3. Open the Collector detail page.
4. Confirm runtime, version, stable identity and `Remote config supported`.

Expected result: one healthy managed Collector with a stable InstanceUID or
logical FleetAMP ID and OpAMP remote-configuration capability.

### 2. Establish administration and ownership

1. Under **Administration → Users & roles**, create `payments-owner` with the
   Group Owner role.
2. Under **Groups**, create:
   - Application: `payment-api`
   - Environment: `demo`
   - Place: `local`
3. Assign `payments-owner` to the group.
4. Assign the Collector's controlled group identity to the same values.

Expected result: the group shows one Collector and the Fleet table displays the
generated group name, not a generic ownership label.

### 3. Verify Group Owner isolation

1. Sign out as Admin and sign in as `payments-owner`.
2. Confirm only the owned group is visible.
3. Attempt to open `/agents`, `/approvals`, `/audit-log` and `/settings/users`.

Expected result: the owner can manage the owned group but receives `403
Forbidden` for global Fleet, approval, audit and Administration pages.

### 4. Create and validate a configuration version

1. Open the owned group.
2. Confirm the latest version is selected as the baseline.
3. Confirm **New version**, **Validate and preview**, and **Validate and save
   version** are initially disabled.
4. Change an editable section, such as a processor setting.
5. Confirm the version and validation controls become enabled.
6. Enter version `0.2.0-demo.1` and select **Validate and preview**.
7. Review the generated complete YAML.
8. Save the validated version.

Negative check: enter malformed YAML in an editable section and confirm the
inline validation error prevents saving.

Expected result: only an actual editable change enables version creation;
protected sections remain unchanged and invalid YAML cannot enter approval.

### 5. Submit the approval request

1. Select the saved version in **Group deployment preview**.
2. Verify the target Collector and readiness result.
3. Select an expiry period and submit for approval.

Expected result: the request records group, requester, validation status,
Collector count, immutable configuration identity, target snapshot and expiry.

### 6. Review as Admin

1. Sign in as Admin and open **Approvals**.
2. Open the request by its version link.
3. Review current versus proposed YAML.
4. Confirm removed lines are red and added lines are green.
5. Approve and deploy.

Expected result: the original requester cannot self-approve; Admin approval
changes the request to deploying and starts delivery to the snapshotted target.

### 7. Verify deployment and runtime evidence

1. Open the group and Collector deployment history.
2. Wait for `applied` status.
3. Compare the central desired version with the agent-reported effective
   configuration.
4. Confirm group drift reports the Collector as in sync.

Expected result: desired and effective state agree and deployment history shows
the requester, approval association and final status.

### 8. Exercise rollback safely

Use a dedicated test Collector. Submit a syntactically valid configuration that
passes the configured validator but is expected to fail only in the controlled
test runtime. Do not weaken validation or use a production Collector merely to
force failure.

Expected result: FleetAMP records the failed deployment, attempts one rollback
to the previous working version and records the rollback outcome. If the
distribution-aware validator rejects the configuration before approval, record
that as a successful safety gate instead of forcing runtime failure.

### 9. Exercise drift

1. With drift policy set to **Report only**, alter the Collector's local/base
   configuration in the lab and reconnect it.
2. Confirm Fleet and Group pages show desired versus effective differences.
3. Review the drift event in **Audit log**.
4. Repeat with **Enforce approved configuration** only in the isolated lab.

Expected result: report-only preserves the detected difference; enforcement
resends the approved central version and records the reconciliation action.

### 10. Verify approval expiry and inventory deletion

1. Create a short-lived approval request in a disposable test database or
   advance its expiry through a test fixture.
2. Confirm it moves to the Expired filter and remains available for audit.
3. Disconnect the demo Collector.
4. Confirm an Admin can delete the disconnected inventory record.
5. Confirm a Group Owner can delete only a disconnected Collector whose every
   assigned group is owned by that user.

Expected result: connected Collectors cannot be deleted, and unassigned
Collectors remain Admin-only.

## Demo acceptance criteria

- Automated smoke test passes without skipped navigation pages.
- Group Owner cannot access global/Admin resources.
- Invalid configuration cannot be saved or submitted.
- Requester cannot approve their own request.
- Approved configuration reaches `applied`, or failure produces recorded
  rollback evidence.
- Drift state is visible at Collector, Group and Audit levels.
- Screenshots contain no credentials, tokens, private URLs or personal data.
