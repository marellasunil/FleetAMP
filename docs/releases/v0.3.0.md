# FleetAMP v0.3.0 — Guided Telemetry Blueprints

FleetAMP v0.3.0 is the planned guided-instrumentation release. Its first implementation turns common observability intents into explicit, reviewable OpenTelemetry Collector configuration while retaining all v0.2.0 governance controls.

## Implemented scope

- A real **Blueprints** page replaces the Upcoming placeholder.
- **OTLP application service** generates selected metrics, traces, and logs pipelines.
- **Host observability** generates a host-metrics pipeline.
- Administrators manage reusable Destination Profiles by name and environment.
- Destination Profiles centrally control exporter component configuration, including endpoint, environment-variable authentication references, and TLS settings.
- Destination Profile exporter configuration is encrypted at rest using the FleetAMP server secret pepper.
- Generated configurations include governed memory-limiter and batch processors.
- Generated YAML passes the normal FleetAMP syntax, structure, and optional Collector-distribution validation.
- Successful output is stored as the existing immutable, group-scoped configuration version.
- A requester can save the version or submit it directly for approval with reviewer, reason, and expiry.
- Group scoping, self-approval prevention, target snapshots, email notification, OpAMP delivery, automatic rollback, drift handling, and audit history reuse the existing services.
- Destination Profile and Blueprint generation activity receives explicit audit event names.

## Release acceptance workflow

1. An Admin creates a test and production Destination Profile using secret environment references rather than literal credentials.
2. A Group Owner confirms that only their assigned groups are visible.
3. The owner creates each Blueprint pattern and confirms the generated configuration is visible in the target group.
4. Invalid destination YAML and an empty OTLP signal selection must be rejected.
5. The owner submits a generated version to a different eligible reviewer.
6. The reviewer compares and approves the immutable version from Approvals.
7. Connected Collectors receive it through OpAMP and report the effective hash.
8. A controlled failed delivery confirms the single automatic rollback attempt and retained deployment history.
9. A controlled local configuration change confirms report-only and enforcement drift behavior.
10. Audit Log confirms destination creation/deletion and Blueprint generation/request events.

## Deferred from v0.3.0

- User-defined Blueprint templates and reusable module composition
- Versioned Destination Profiles and in-use deletion protection
- Secret-manager integrations (the initial release expects environment-variable references)
- Canary and staged rollout orchestration
- Full instrumentation guides and SDK/operator automation
- Visual Blueprint editor and policy-as-code engine

## Upgrade notes

- Existing SQLite databases gain the `destination_profiles` table automatically.
- Existing configurations, approvals, deployments, and groups are unchanged.
- Create at least one enabled ownership group and Destination Profile before using the builder.
- Configure `FLEETAMP_OTELCOL_BINARY` to validate generated output against the exact Collector distribution used by managed agents.
- Back up the data directory and SQLite database before upgrading, as for every pre-1.0 release.


## Pattern and component-block catalog

Administrators manage the inputs available to the guided builder:

- **Patterns** define the platform, supported signals and base receiver configuration.
- **Component blocks** are reusable receivers, processors, extensions or connectors.
- Blocks may be optional, required by default, or locked by an administrator.
- Enabled blocks appear in the Blueprint builder. This lets an administrator add
  a missing capability such as `memory_limiter` without changing application code.
- Destination Profiles remain separate so exporter endpoints, TLS and credentials
  stay administrator-controlled.

A generated Blueprint is still stored as an immutable group configuration and
continues through the existing validation, approval, deployment, rollback, drift
and audit workflow.


## Guided visual Blueprint journey

The Blueprint builder follows the customer-centric journey:

1. Select the observability goal.
2. Describe platform, technology and preferred instrumentation method.
3. Receive deterministic instrumentation and Pattern recommendations.
4. Select telemetry signals, approved Blocks, destination and authorized group.
5. Review implementation instructions and the live end-to-end telemetry flow.
6. Generate and validate governed Collector configuration.
7. Save an immutable version or submit it for approval.
8. Deploy through FleetAMP and continue with status, rollback, drift and audit.

The flow preview shows workload → instrumentation → Pattern/Collector processing →
approved destination → target group. Recommendations are deterministic in v0.3.0;
a future AI assistant can enhance them without changing the governed workflow.
