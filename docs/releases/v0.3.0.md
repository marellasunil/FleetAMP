# FleetAMP v0.3.0 — Instrumentation Guides

FleetAMP v0.3.0 introduces a guided OpenTelemetry decision experience while keeping configuration generation separate from educational guidance.

## Instrumentation Guides

The **Guides** page provides a progressive visual decision map:

1. Select an observability capability.
2. Select the workload platform.
3. Select the technology or telemetry source.
4. Select the instrumentation or collection method.
5. Select the deployment topology.
6. Review advantages, requirements, considerations and implementation direction.

Each choice is a radio node. FleetAMP reveals only the next relevant connected branch and stops when the recommendation is complete. It no longer forces every capability through application technology, instrumentation and deployment stages. Animated multi-arrow connectors run from the selected node to every compatible option in the next stage; the chosen path is highlighted. Connectors redraw on resize and scrolling, and animation is disabled when the user prefers reduced motion. Changing an earlier answer clears incompatible downstream choices.

The built-in paths are intent-specific:

| Capability | Decision path |
| --- | --- |
| Application performance | Capability → platform → application technology → instrumentation → deployment topology |
| Infrastructure | Capability → platform → infrastructure metrics |
| Kubernetes | Capability → cluster environment → Kubernetes telemetry → collection component → Collector placement |
| Logs | Capability → platform → log source → collection approach → Collector placement |
| Database | Capability → database platform → database engine → collection approach → Collector placement |
| Frontend | Capability → client platform → frontend technology → instrumentation → export topology |
| Custom telemetry | Capability → telemetry platform → telemetry source → collection approach → Collector placement |

Initial capability coverage includes:

- Application performance
- Infrastructure
- Kubernetes
- Logs
- Databases
- Frontend
- Custom telemetry

The guide covers language auto-instrumentation, OpenTelemetry SDKs, Collector receivers, eBPF/OBI, host agents, Operator injection, DaemonSets, sidecars, gateways and direct OTLP export.

The catalog is aligned with the current OpenTelemetry zero-code language guidance, Collector receiver registry and Kubernetes Collector components. Component availability and maturity still depend on the Collector distribution and version deployed by the organization.

The page is advisory. It does not create, version, approve or deploy configuration.

## Organization-managed Guide Catalog

Administrators can customize the decision map from **Administration → Guide Catalog**. They can add, edit, disable or delete nodes, connect each node to one or more choices in the preceding stage, and provide organization-specific descriptions, advantages, requirements, considerations and implementation steps.

Changes are made in a draft and validated before they are saved or published. Visitors continue to see the current published version until an administrator publishes the draft. Every publication is an immutable snapshot; the history can be rolled back without deleting intervening versions, and all mutations are recorded by the audit middleware.

## Common Blueprint catalog

The **Blueprints** page now offers six common organizational starting points: Application APM, Linux Host Baseline, Kubernetes Cluster Baseline, Central OTLP Gateway, Application Logs and Prometheus Metrics.

Selecting a Blueprint shows its recommended topology, outcomes, prerequisites and generated Collector YAML, including receivers, governed processors and pipelines. Selecting an administrator-controlled Destination Profile updates the exporter section with non-sensitive profile settings while masking literal credentials. Users then select an accessible group, validate the configuration, save an immutable version and can submit it to the existing approval workflow.

Administrators and assigned Group Owners can manage encrypted, write-only group secrets. Configuration uses `${secret:key}` references; FleetAMP verifies that referenced keys exist and substitutes plaintext only in the OpAMP delivery payload. Saved versions, previews, approval diffs, audit details and drift views retain safe references or normalized markers instead of values.

Groups link directly to the Blueprint catalog with the target group preselected. The group configuration editor loads the latest successfully deployed version, rejects unchanged copies and requires a new version whenever configuration content changes. Group deployment history excludes automatic reconcile operations, which remain available in Audit logs.

## Workflow

The relationship is:

1. **Guide** — understand and select an instrumentation approach.
2. **Pattern** — choose a reusable administrator-governed starting point.
3. **Blueprint** — compose and preview the required configuration.
4. **Validation and approval** — create an immutable version and submit it through governance.
5. **Deployment** — deliver through FleetAMP with status, rollback, drift and audit.

## Upgrade notes

- Existing configurations, groups, approvals, deployments and audit history are unchanged.
- FleetAMP creates the Guide draft, active-version pointer and immutable version-history tables automatically. The initial catalog is seeded from the built-in v0.3 guide.
- Existing Pattern, Block and Destination Profile storage is retained. Missing common Patterns and required safety Blocks are seeded without overwriting organization-managed catalog entries.

## Governed GitOps dry-run worker

Approved immutable GitOps previews can enter an execution outbox. The optional
worker claims one queued request with a time-limited lease so multiple FleetAMP
instances cannot process the same request concurrently. It verifies the stored
preview evidence, selects a provider-neutral adapter, and appends claimed and
completed events without modifying the immutable request.

v0.3 registers a no-op adapter for GitHub, GitLab and Azure DevOps. It records
the provider, mode, branch, repository path and file count as dry-run evidence;
it does not read credentials, call provider APIs, create commits, or create pull
requests. The worker is disabled by default and is enabled with
`FLEETAMP_GITOPS_WORKER_ENABLED=true`. The worker ID, poll interval and lease
duration can be set with `FLEETAMP_GITOPS_WORKER_ID`,
`FLEETAMP_GITOPS_WORKER_INTERVAL` and `FLEETAMP_GITOPS_LEASE_TTL`.

GitHub pull-request delivery is separately guarded by
`FLEETAMP_GITOPS_GITHUB_WRITES_ENABLED=true`. When it is disabled, GitHub,
GitLab and Azure DevOps all remain dry-run adapters. A connection reference such
as `secret://github/production` is resolved at execution time from
`FLEETAMP_GITOPS_SECRET_GITHUB_PRODUCTION`; the token is never copied into a
preview, approval, execution request or audit evidence. The GitHub adapter only
supports `fleetamp-pull-request` mode: it creates or reuses the deterministic
`fleetamp/<execution-id>` branch, writes exactly the approved preview files and
creates or reuses a pull request against the configured base branch. Use a
fine-grained token limited to the selected repository with Contents read/write
and Pull requests read/write permissions.

### Retry and worker recovery

GitOps execution requests remain immutable while their status history is
append-only. If a worker stops after claiming an execution, another worker may
reclaim the same execution only after its lease expires. This reuses the same
execution ID and deterministic provider branch, preventing a recovery from
creating a second pull request.

Administrators may retry a failed execution from the GitOps execution monitor
only after providing a reason. FleetAMP records the actor, reason and attempt
number as a new queued event and allows at most three total attempts. Queued,
claimed, successful or already exhausted executions cannot be retried.
